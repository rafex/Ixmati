# Evidencia — 150/s no sostenible con el baseline anterior

## Identidad

- SHA del artefacto Debian amd64: `907236f12e92e691bde46c784cc3427eeaecd3af`
- Harness publicado posteriormente en `de903b1`
- Escenario: `150` solicitudes/s, REST/JSON, `ack_mode=committed`
- Concurrencia: `1000`
- Generador: contenedor separado dentro del mismo host Podman
- Evidencia raw: `spec-native/evidence/raw/soak-150-20260813T030822Z/`
- Duración observada: `900` segundos

## Resultado al minuto 15

| Métrica | Resultado |
|---|---:|
| Solicitudes enviadas | 135,051 |
| Throughput controlado | 150.0/s |
| Saturación del generador | 0 ticks |
| HTTP `200` | 123,017 |
| HTTP `202/PENDING` | 10,526 |
| HTTP `429` | 1,501 |
| Confirmación durable `200` | 91.1% |
| `consumer_queue_depth` | 1 en el snapshot |
| `cache_sync_queue_depth` | 0 |
| SQLite | `integrity_check=ok` |

El generador mantuvo la tasa objetivo y no fue el límite artificial. Los
`202` correspondieron a expiraciones de la ventana de confirmación durable de
2 segundos; los `429` fueron backpressure del API. El writer y SQLite
continuaron progresando, pero el porcentaje de confirmaciones `200` quedó
muy por debajo del 99.5% requerido.

## Clasificación

El escalón se clasificó como **no sostenible como capacidad durable de
producción**. La ejecución se detuvo después de 15 minutos, una vez que el
fallo del criterio de confirmación era concluyente; no se presenta como una
soak completa de una hora ni como evidencia de estabilidad horaria.

La prueba no observó corrupción ni pérdida durante este intervalo. Tampoco
demuestra que 150/s sea imposible con otra configuración: el siguiente ensayo
debe usar el SHA `28245fd`, que cambia la espera de ACK durable para no retener
un hilo bloqueante por petición concurrente.
